# Preza

Публикация нескольких PDF-презентаций по отдельным ссылкам на **preza.shmoza.net**.
FastAPI + SQLite + Poppler; интерфейс на HTML/CSS/JS без отдельной сборки.

## Работа с презентациями

- `/admin` — вход по одному Access Key, библиотека презентаций, создание,
  редактирование названия/адреса/настроек, замена PDF и удаление.
- `/p/<slug>` — страница одной презентации. Публичного каталога нет; `/` ведет
  на вход в админку.
- Вид **«Непрерывная лента»** сохраняет вертикальное отображение без промежутков.
- Вид **«Отдельные слайды»** показывает один слайд на всю ширину окна.
  Переключение — кнопками и стрелками ←/→.
- Автор выбирает вид по умолчанию и разрешает или запрещает смену вида.
- Необязательный пароль для зрителей принимает любое непустое значение,
  включая `1111`. Ограничений сложности нет; пробелы и регистр сохраняются.
  Пароль защищает API, изображения и поток событий. После смены пароля
  открытые сеансы зрителей теряют доступ.
- **«Начать показ»** в превью включает управление ведущим. Все зрители видят
  текущий слайд, включая подключившихся позже, и не могут переключать его или
  вид просмотра. SSE доставляет изменения сразу и восстанавливает соединение.
  **«Завершить показ»** возвращает обычный просмотр.
- PDF заменяется после успешной конвертации; ошибка сохраняет прежний документ.
  Замена PDF завершает текущий показ. Конкурирующее редактирование дает конфликт,
  предлагая открыть актуальные настройки.

При первом запуске старая презентация из `source/current.pdf` и `slides/`
импортируется в `/p/presentation`; `/view` перенаправляет на нее. Старые файлы
сохраняются. Удаленная импортированная презентация повторно не создается.

## Локальный запуск из исходников

```sh
cp .env.example .env
# Заполните ADMIN_ACCESS_KEY и сгенерируйте SESSION_SECRET.
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
docker compose up -d --build
```

Откройте `http://127.0.0.1:18480/admin`. `PUBLIC_URL` должен точно совпадать с
адресом браузера: например, `localhost` и `127.0.0.1` — разные origin.
Для серверного запуска используется описанный ниже подписанный релиз.

## Быстрый production-деплой

Сервер заранее подготовлен: Debian 12+ / Ubuntu 22.04+, amd64 или arm64,
Docker Engine, Docker Compose **2.30+**, существующий серверный nginx.
Порты 80/443 и TLS принадлежат nginx; приложение публикует только loopback.

Первый релиз имеет имя `preza-v0.0.1`. Команда ниже работает **после публикации
этого релиза**, а не загружает код из ветки:

```sh
# 1. Подготовить и проверить точный релиз, не запускать приложение.
curl -fsSL \
  https://github.com/psewdon1m/preza/releases/download/preza-v0.0.1/bootstrap.sh \
  | sudo sh

# 2. Изменить только OPERATOR INPUT. ACCESS_KEY изначально пуст.
sudoedit /opt/exocortex/preza/.env

# 3. Установить и проверить локально.
sudo chmod 600 /opt/exocortex/preza/.env
sudo preza-install
sudo preza-install status
curl -fsS http://127.0.0.1:18480/api/health
```

Bootstrap содержит публичный ключ релиза, проверяет подпись manifest и SHA-256
пакета до извлечения, не применяет архивные права/владельцев и запрещает обход
путей и ссылки. Он устанавливает доверие в
`/etc/exocortex/release-trust/preza.pem`, готовит `/opt/exocortex/preza` и
команду `/usr/local/bin/preza-install`. Повторный bootstrap не перезаписывает
установку или несовпадающий ключ.

`.env` имеет четыре секции: `OPERATOR INPUT`, сгенерированные секреты, блокировка
релиза, параметры runtime. Значения читаются как буквальный текст, без исполнения
shell; двойные кавычки используют синтаксис JSON, например `ACCESS_KEY=" 1111 "`.
Access Key не имеет требований к длине, сложности или алфавиту. Установщик
создает verifier; контейнер получает verifier вместо исходного ключа.
`.env`, `runtime.env` и блокировка деплоя — root-owned, mode 0600.
`DATA_VOLUME` выбирается при первой установке; последующая смена требует
отдельного переноса данных и не выполняется обычным install/update.

Установщик проверяет свободный локальный порт, подтягивает образ по digest,
проверяет Compose, запускает сервис и ожидает здоровую версию ограниченное время.
Контейнер работает от UID/GID 10001, с read-only root, без capabilities,
с `no-new-privileges`, ограничениями ресурсов и ротацией логов.

## Подключение к серверному nginx

Только **после** успешной локальной проверки оператор подключает
[nginx/preza.conf](nginx/preza.conf). Это отдельный vhost, совместимый с
предоставленным `.nginx/exocortex.conf`: домен и upstream выделены отдельно,
`default_server` и глобальный nginx.conf не меняются.

Сервер заранее получает сертификат для `preza.shmoza.net` своим существующим
способом. Конфиг ожидает:

```text
/etc/letsencrypt/live/preza.shmoza.net/fullchain.pem
/etc/letsencrypt/live/preza.shmoza.net/privkey.pem
```

При другом пути сертификата или `LISTEN_PORT` измените **кандидат** конфигурации.
Из `.env` nginx ничего не читает. Установщик не устанавливает, не запускает
и не перезагружает nginx или Certbot.

```sh
sudo cp /opt/exocortex/preza/current/nginx/preza.conf \
  /etc/nginx/sites-available/preza.conf
sudo ln -s /etc/nginx/sites-available/preza.conf \
  /etc/nginx/sites-enabled/preza.conf
sudo nginx -t
# Только если проверка успешна:
sudo systemctl reload nginx
```

При неудачной проверке отключите добавленную ссылку и сохраните предыдущий
рабочий конфиг. На сервере с другой системой include используйте ее штатный путь.
Затем проверьте `https://preza.shmoza.net/admin` с внешнего клиента с обычной
проверкой TLS. `/api/health` через публичный ingress доступен только loopback.

## Внутренние обновления

Preza имеет собственный установщик и **не взаимодействует с Exocortex Updater**,
не регистрирует профиль и не устанавливает shared agents. Это согласованное
для данного проекта исключение из пунктов 21.5–21.7 Part 04.

```sh
sudo preza-install update 0.0.2
sudo preza-install status
```

Обновление проверяет точный подписанный релиз уже закрепленным ключом, сначала
подтягивает образ и проверяет Compose, затем останавливает приложение на время
копирования данных и смены версии. При неуспешном запуске автоматически
восстанавливает предыдущую версию **и ее данные**. Изменение nginx не выполняется.

Резервные копии данных лежат в `/opt/exocortex/preza/backups/`; `.env` в них
не входит. Перенос секретов на другой сервер — отдельная защищенная процедура.
После прерывания во время переключения версии установщик требует:

```sh
sudo preza-install rollback
```

Эта команда также откатывает последнее успешное обновление. Она восстанавливает
данные на момент обновления, поэтому более поздние изменения презентаций будут
заменены резервной копией. Сохраняйте нужные данные перед ручным откатом.
Удаление старых копий/релизов остается за оператором.

## Переход со старого контейнерного nginx

1. Сделайте резервную копию старого Docker volume. Остановите старые контейнеры
   **этого проекта** из старого checkout; не выполняйте `down -v`.
2. Узнайте фактическое имя volume через `docker volume ls`. По умолчанию
   ожидается `preza_presentation_data`; другое имя укажите в `DATA_VOLUME`.
3. Выполните bootstrap и установку. Установщик готовит права volume для UID 10001,
   а приложение импортирует старые слайды.
4. Подключите отдельный серверный vhost и проверьте новую страницу и `/view`.

Старые контейнерные сертификаты автоматически в серверный nginx не переносятся.
Установщик не удаляет старые nginx/Certbot volumes и соседние сервисы.

## Выпуск подписанного релиза

В репозитории подготовлены `.github/workflows/check.yml` и `release.yml`.
Перед первым выпуском владелец:

1. Добавляет подготовленный приватный RSA-ключ подписи в GitHub Environment
   `release` как secret `PREZA_RELEASE_SIGNING_KEY`: Settings → Environments →
   release → Environment secrets → Add secret. Значение — весь PEM, включая
   строки `BEGIN PRIVATE KEY` и `END PRIVATE KEY`. Приватный ключ хранится вне
   репозитория; в Git входит только открытый [.release/public-key.pem](.release/public-key.pem).
   Actions проверяет соответствие секретного ключа закрепленному открытому ключу
   до сборки образа. Сохраните защищенную резервную копию приватного ключа для
   будущих релизов; повторно генерировать ключ при обновлениях не нужно.
2. Включает immutable releases для репозитория и защищает environment `release`.
3. Обеспечивает публичную доступность пакета `ghcr.io/psewdon1m/preza`,
   чтобы сервер мог подтянуть digest без чужих учетных данных.
4. Публикует проверенный тег `preza-v0.0.1`. Actions тестирует код, собирает
   образ для amd64/arm64, подписывает manifest и выпускает bootstrap и пакет.
   Повторная публикация того же тега не заменяет release assets.

Для подготовки артефактов вручную, после публикации образа:

```sh
python3 scripts/build_release.py --version 0.0.1 \
  --image ghcr.io/psewdon1m/preza@sha256:FULL_IMAGE_DIGEST \
  --signing-key /secure/preza-signing.pem --output dist
```

Неподписанные, неполные или измененные пакеты установщик не принимает.
Смена ключа требует отдельной явной процедуры; обычный update не меняет доверие.

## Проверки

```sh
docker build --target test -t preza-test -f api/Dockerfile .
docker run --rm preza-test
node --check web/admin.js
node --check web/view.js
```

Тесты выполняют настоящую конвертацию PDF, проверяют разделение презентаций,
пароли и CSRF, сохранность данных при ошибках, миграцию старого volume,
SSE с несколькими зрителями, подпись и извлечение релизов.
